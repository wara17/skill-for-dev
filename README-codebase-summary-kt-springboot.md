# สกิล Codebase Summary — Kotlin / Spring Boot

**ชื่อสกิล:** `codebase-summary-kt-springboot`

## สกิลนี้ทำอะไร

สแกน repo ที่เขียนด้วย Kotlin + Spring Boot แล้วสรุปออกมาเป็นไฟล์ `CODEBASE.md`
(หรือหลายไฟล์ถ้า repo ใหญ่) ที่กระชับพอให้ AI งานอื่น ๆ โหลดไปใช้แทนการไล่อ่านโค้ดทั้ง repo
ใหม่ทุกครั้ง เป้าหมายคือ **จ่ายต้นทุนสแกนครั้งเดียว** แล้วให้ทุก task ถัดไปหยิบไฟล์นี้ไปใช้ต่อ
โดยไม่ต้อง re-index repo ซ้ำ

ไฟล์ผลลัพธ์ไม่ใช่เอกสารอ้างอิงละเอียด (ห้ามยาวเกิน ~150 บรรทัดต่อไฟล์, ห้ามก็อปซอร์สโค้ดเต็ม
หรืออธิบายทีละฟังก์ชัน) — เน้นให้ AI รู้ "โครงสร้าง + กติกาของทีม" พอจะเขียนโค้ดต่อได้ถูกทาง
ไม่ใช่รู้รายละเอียด business logic ทุกจุด

## ทำงานยังไง — ตัดสินใจโหมดเองอัตโนมัติ

เรียกสกิลเดียวกันทุกครั้ง ไม่มีคำสั่งแยก "generate" กับ "update" — ตัวสกิลเช็คเองว่า
`docs/codebase/CODEBASE.md` มีอยู่แล้วหรือยัง แล้วเลือกโหมดเอง:

- **ไม่มีไฟล์ → Generate mode**: สแกนเต็ม 7 หัวข้อ (ด้านล่าง) แล้วสร้างไฟล์ขึ้นใหม่
- **มีไฟล์แล้ว → Update mode**: ไม่สแกนซ้ำทั้งหมด อ่านแค่ว่า commit ล่าสุดเปลี่ยนอะไรไปบ้าง
  (`git diff`) แล้วแก้เฉพาะ section ที่ได้รับผลกระทบ
- **user สั่งให้ regenerate ใหม่ทั้งหมดเอง** แม้ไฟล์จะมีอยู่แล้ว → เคารพคำสั่งนั้น ข้ามไป
  Generate mode ตรง ๆ (เผื่อเคสที่การเปลี่ยนแปลงมีผลกระทบสูงแต่จำนวนไฟล์ที่เปลี่ยนน้อย
  จนระบบอัตโนมัติตรวจไม่เจอ)

## สแกนอะไรบ้าง (Generate mode)

1. **Build & config** — version, dependency, ตัวแปร config ที่มีผลต่อพฤติกรรม, commit sha ปัจจุบัน
2. **Entry point & layering** — layering convention จริงที่ repo ใช้ และทิศทางที่ layer หนึ่งอนุญาต
   ให้เรียก layer ไหนได้บ้าง
3. **API layer** — endpoint, error-handling pattern, MVC หรือ WebFlux, วิธี map DTO, วิธี validate
4. **Service & domain layer** — responsibility ของแต่ละ service, Kotlin idiom ที่ทีมใช้จริง
   (null-safety, coroutine), ขอบเขตของ `@Transactional`
5. **Data layer** — entity, ความสัมพันธ์, วิธี generate ID, ชื่อไฟล์ migration
6. **Cross-cutting** — security, Kafka/Redis, และ**คำสั่งรันเทสต์ตัวจริง** (จุดสำคัญ เพราะสกิล
   `dev-workflow` อ่านค่านี้ไปใช้รันเทสต์โดยตรง)
7. **Conventions** — naming, lint command, พื้นที่ legacy ที่ห้ามแตะ, รูปแบบ commit/branch

ทุกข้อจบด้วยการลงในไฟล์ output ตาม template ที่กำหนดไว้ตายตัว (Stack / Structure / API
surface / Domain & Service / Data layer / Testing / Security & Integrations / Conventions /
⚠️ Watch out)

## โครงสร้างไฟล์ที่ได้

- **repo เล็ก/กลาง**: ไฟล์เดียว `docs/codebase/CODEBASE.md`
- **repo ใหญ่** (multi-module หรือมากกว่า ~50 ไฟล์ต่อโมดูล): แตกเป็นหลายไฟล์ —
  `CODEBASE.md` เป็นแค่ overview ชี้ทางไปยัง `summary-{module}.md` ของแต่ละโมดูล เพื่อให้
  task ที่แก้แค่โมดูลเดียวโหลดแค่ไฟล์ที่เกี่ยวข้อง ไม่ต้องโหลดทุกโมดูลเข้า context

## เชื่อมกับ Copilot ยังไง

หลังสร้าง `CODEBASE.md` ครั้งแรก สกิลจะสร้าง/เติมข้อความสั้น ๆ ลงใน
`.github/copilot-instructions.md` (ไฟล์ที่ Copilot Chat อ่านจริงในทุก IDE) บอกว่า
"ให้อ่าน CODEBASE.md ก่อนเสมอเวลาจะแตะโค้ดเดิม ถ้าไม่มีหรือเก่าเกิน 2 สัปดาห์ ให้รันสกิลนี้ก่อน"
— ทำให้ทุก task ที่ผ่าน Copilot ถูกเตือนอัตโนมัติโดยไม่ต้องมีใครมาสั่งเอง

## ดูแลตัวเองยังไงไม่ให้เก่า

- เช็คว่าควร refresh ไหมด้วยวิธีที่ถูกที่สุด — แค่เทียบวันที่ใน header (เกิน 2 สัปดาห์ = ถือว่าเก่า)
  ไม่ต้องรัน git command เพิ่ม
- พอจะ refresh จริง ค่อยรัน `git diff` เพื่อดูว่าเปลี่ยนไปมากแค่ไหน — เปลี่ยนน้อย (ต่ำกว่า ~30%
  ของไฟล์ในกลุ่มที่เกี่ยวข้อง) แค่ patch เฉพาะ section ที่กระทบ, เปลี่ยนเยอะหรือโครงสร้างเปลี่ยน
  ไปเลย → แนะนำให้ regenerate ใหม่ทั้งไฟล์แทน

## เมื่อเจอเคสไม่ชัดเจน

ถ้าเจอ MVC กับ WebFlux ปนกันในโปรเจกต์เดียว, layering ไม่เข้าพวกไหนเลย, หรือแต่ละโมดูล
ใช้ convention ไม่ตรงกัน — สกิลนี้ถูกกำหนดให้**บันทึกความไม่ชัดเจนนั้นลง ⚠️ Watch out ตรง ๆ**
แทนที่จะเดาคำตอบเดียวแล้วนำเสนอเป็นความจริง เพราะ task อื่นที่มาอ่านไฟล์นี้ทีหลังจะเชื่อไปเลย
โดยไม่ตรวจซ้ำ — คำตอบผิดแบบมั่นใจอันตรายกว่าคำตอบที่บอกตรง ๆ ว่าไม่ชัวร์

## ข้อจำกัดที่ควรรู้

- ครอบคลุมเฉพาะ Kotlin + Spring Boot เท่านั้น ไม่ใช่ pattern กลางสำหรับ stack อื่น
- ถ้า repo ไม่มี git หรือเป็น shallow clone จะลดไปใช้การเช็คแบบวันที่ล้วน (ไม่มี commit-based
  tracking ให้)
- สกิล `dev-workflow` อ่านคำสั่งรันเทสต์จากไฟล์นี้โดยตรง แต่ยังไม่ได้บังคับให้รัน lint command
  ที่ไฟล์นี้จับไว้ก่อนถือว่างานเสร็จ — เป็นจุดที่ต้องไปแก้ที่ฝั่ง `dev-workflow` แยกต่างหาก
